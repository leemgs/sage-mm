# Cover Letter — Software: Practice and Experience

To: The Editor-in-Chief, *Software: Practice and Experience*

Dear Editor,

Please find enclosed my manuscript, **"SAGE-MM: Cross-Layer Coordination of
Managed Heap, Native Interop, and Page Reclamation for Managed Runtimes under
Fixed Memory Budgets,"** which I submit for consideration as a regular paper in
*Software: Practice and Experience*.

## What the paper is about

Memory-constrained embedded devices increasingly run managed (.NET/CoreCLR)
application stacks inside a single, swapless process budget. Within that budget
one application co-locates a garbage-collected heap, native interoperability
buffers, and a working set of file-backed executable code pages. In practice
these three layers are tuned in isolation, which is locally reasonable but
globally fragile: enlarging the nursery lowers collection frequency but raises
footprint; removing managed allocations shifts cost to native marshalling; and
reclaiming clean code pages lowers residency but can reintroduce refault-driven
latency spikes during rapid application switching.

SAGE-MM is a **cross-layer coordination design for managed runtimes**, not a new
garbage collector. It separates a launch-time heap-configuration decision and a
reviewed source-time interop decision from a single, deliberately narrow online
controller that adjusts only one reclamation interval and one compaction gate,
with dimensionless telemetry, hysteresis, a cooldown, a causal (prequential)
update order, fail-closed handling of invalid telemetry, and an explicit
non-learning threshold fallback.

## Why it fits Software: Practice and Experience

The work is squarely a systems-software contribution: it concerns the practical
engineering of managed-runtime memory behavior (heap, interop, and OS page
reclamation) on real software stacks, and it is evaluated by measurement rather
than simulation. The implementation, the measurement pipeline, and the released
per-run dataset make the results reproducible, which matches the journal's
emphasis on practice and experience with real software systems.

## Principal contributions and measured findings

- A cross-layer action boundary that distinguishes launch-time, source-time, and
  online interventions, so that only the controller adapts at runtime.
- An implementable controller with a causal (prequential) update order, bounded
  actions, and fail-closed guards.
- A measured ablation and policy comparison over the coordination ladder on a
  representative embedded managed-runtime platform (a Tizen 10.0 image and its
  .NET 8 / CoreCLR runtime on a Raspberry Pi 4 Model B), evaluated across its 32-
  and 64-bit builds, with 30 independent runs per condition and 95% percentile
  bootstrap confidence intervals. Under a favorable workload the fully
  coordinated design lowers peak memory footprint by about 24% and GC tail pause
  by 37–38% (set by the static layers) while the online controller recovers most
  of the refault cost of static reclamation at roughly 1% controller CPU.
- A robustness study across favorable, neutral, and adverse workload regimes
  showing the design is fail-safe where no gain exists and only bounded-negative
  where reclamation backfires, with an adverse-regime supervisor that detects the
  bad regime within seconds and eliminates the observed out-of-memory events.

## Reproducibility and integrity

Every reported number is generated by a fail-closed pipeline directly from a
per-run measurement bundle; the build refuses to mark itself submission-ready
unless genuine measurements are supplied, and no estimated or predicted value is
ever substituted for missing data. The full per-run dataset is publicly archived
on Zenodo under DOI 10.5281/zenodo.22918517. I state explicitly which parts of
the protocol (per-architecture heap sweeps, isolated interop benchmarks, and
multi-hour endurance) are future work rather than reported results.
